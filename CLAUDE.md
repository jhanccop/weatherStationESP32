# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

PlatformIO/Arduino firmware for a battery-powered weather station built on a generic ESP32 Dev Module + SIM800 LTE/GPRS modem (via hardware `Serial2`, RX2=16/TX2=17), a DHT21/AM2301 temp/humidity sensor wired as `DHT_TYPE DHT21` (GPIO4 — despite the "DHT22" naming in comments/filenames, the actual sensor type compiled in is DHT21), a wind-direction encoder selectable in software between MT6701 and AS5600 over I2C (SDA=21/SCL=22), a Hall-effect pulse-counting anemometer (GPIO13), a Hall-effect rain bucket on an input-only pin with no internal pull resistor (GPIO39, EXT1 wakeup; the board adds an external 10k pull-up R8 to 3.3V), an SD card on the default VSPI pins (MISO19/MOSI23/SCK18/CS5), a resistive battery divider on an ADC pin (GPIO34, R10=330k/R11=100k), a 0.96" SSD1306 OLED on the same I2C bus (0x3C, powered from the switched sensor rail), and two buttons — BUT1 "ok" GPIO35 and BUT2 "up" GPIO27 (external 100k pull-ups, active LOW). Sensor power is gated by a P-channel MOSFET on GPIO2 (LOW=ON/HIGH=OFF). Modem power on GPIO15 (`sim_control`) goes through an NPN (Q4) before its P-channel MOSFET, so it is **HIGH=ON/LOW=OFF** (`MODEM_PWR_ON`/`MODEM_PWR_OFF`) and powers only the modem. The 12V SX1308 boost for the RS485 sensor has its own enable on **GPIO14** (`RS485_PWR_PIN`, assumed HIGH=ON, held LOW through deep sleep and forced LOW in `initVariant()`). An auto-direction TTL-RS485 module on UART1 (`Serial1`, GPIO32 TX / GPIO33 RX) reads one Modbus RTU sensor selected by `rs485Type`. The schematic also routes an aux UART (GPIO25/26) that the firmware does not drive yet; there is no ultrasonic sensor any more (GPIO14 was its TRIG). All logic lives in the single file `src/main.cpp`. There is no test suite (`test/` is the empty PlatformIO scaffold) and no application-level lint config. Code comments are in Spanish.

An earlier hardware revision used a LilyGO T-SIM7000G with different pins, RS485 solar radiation, and an SHT30 sensor — that variant has been fully replaced; don't assume old pin numbers or sensors from git history/memory still apply. Pin roles have also shifted *within* this revision (e.g. sensor power MOSFET moved from GPIO13 to GPIO2, freeing GPIO13 for the anemometer) — trust the `#define`s and the pinout comment block at the top of `main.cpp` over older memory of this file.

## Build / common commands

This is a PlatformIO project (not plain Arduino IDE), env name `esp32dev` defined in `platformio.ini`.

```bash
pio run                  # build
pio run -t upload        # build + flash over USB
pio run -t upload --upload-port /dev/ttyUSB0   # flash to a specific port
pio device monitor -b 115200   # serial monitor (matches Serial.begin(115200) in setup())
pio run -t clean         # clean build
```

There are no unit tests; validation is done by flashing and observing serial logs / the on-device web UI.

### Library dependencies live in `platformio.ini`

All third-party libraries are declared as `lib_deps` in `platformio.ini` and resolve from the PlatformIO registry — the project does **not** rely on `~/Arduino/libraries/` (an earlier revision did, informally, and the build was actually broken because of it; `pio run` failed with a missing `ArduinoJson.h` until `lib_deps` was added). Notable pins:
- `ArduinoJson @ ^6.21.5` — pinned to v6 because the code uses the v6 API (`StaticJsonDocument`, `DynamicJsonDocument`, `.containsKey()`), which v7 removed/deprecated.
- `me-no-dev/AsyncTCP @ ^1.1.1` + `me-no-dev/ESPAsyncWebServer @ ^1.2.3` — pinned to the old 1.2.x line, which predates the v3 rewrite that requires ArduinoJson 7.
- `i-am-engineer/MT6701-arduino` + `robtillaart/AS5600` — both wind-direction encoder drivers are always compiled in; which one is actually read at runtime is chosen by `dirSensorType`, not by a build flag.

If you add a new sensor library, prefer adding it to `lib_deps` over installing it globally, so the build stays reproducible on a fresh machine. Verify with `pio run` after any dependency change — version mismatches between PubSubClient/ArduinoJson/ESPAsyncWebServer are a common source of build breaks here.

## Architecture

Single-file event-driven firmware structured around ESP32 deep sleep cycles. Read top-to-bottom in `src/main.cpp`, sections are marked with `/* ====== ... ====== */` banners.

### Power cycle (the core design)

The device spends almost all its time in `esp_deep_sleep_start()`. Each wake does one of three things, dispatched from `wakeup_reason()` (called from `setup()`):

- **Timer wakeup** → `init_running()`: normal cycle — read sensors, send data, go back to sleep.
- **EXT1 wakeup (GPIO39, rain bucket pulse)** → `runRainCounter()`: increments a SPIFFS-persisted rain counter, computes *remaining* sleep time so the next scheduled timer wake stays on schedule, then sleeps again. Uses `RTC_DATA_ATTR cycle_start_rtc` / `cycle_active` (survive deep sleep) plus `getRtcTimeSeconds()` (reads the ESP32 RTC slow clock directly) to track elapsed time across sleep/wake without a wall clock. Since EXT1 only fires when the pin was already LOW (field present), the wake itself is treated as ground truth — the only remaining filter is `RTC_DATA_ATTR lastRainPulseRtcTicks`, which enforces a 300 ms minimum interval (`RAIN_PULSE_MIN_INTERVAL_MS`) between counted tips so wakeup re-arming on a bouncing pin doesn't double-count one real tip. If the configured sleep period has already elapsed by the time a rain wake is serviced, it falls through to running the pending `init_running()` cycle immediately instead of just rescheduling — otherwise a noisy GPIO39 (no external pull resistor on this pin) could keep deferring the real sensor/send cycle indefinitely.
- **EXT0 wakeup (GPIO35, "ok" button)** → `runStatusViewer()`: shows the last cycle's summary (kept in `RTC_DATA_ATTR lastDataJson`/`lastNetStatus`/`lastSignal`) on the OLED, then `sleepRemainingCycle()` — the same keep-the-schedule logic the rain path uses. A 2 s press runs `init_running()` immediately.
- **First boot / undefined wakeup** → also routed through `init_running()`.

`init_running()` itself branches on a hardware pin (`pinConfigAP`, GPIO36 — input-only, no internal pull, requires an external pull-up to 3.3V; the config button pulls it to GND): if held LOW across 10 debounced reads at boot, the device enters **config mode** (`setting()` — starts a WiFi AP + `ESPAsyncWebServer` config portal) instead of the sensor/send/sleep cycle.

GPIO state (the power switches on GPIO2/GPIO15/GPIO14, the LED, and RX2/TX2) is preserved across deep sleep using `gpio_hold_en()`/`gpio_hold_dis()` + `gpio_deep_sleep_hold_en()`. Any new code that drives those pins must release the hold before changing the pin and re-enable it before sleeping, or the new state won't stick / will conflict with prior state. `modemLinesOff()` forces RX2/TX2 to output-LOW-and-held whenever the modem isn't in use (including every sleep, regardless of connection type) — leaving them floating or HIGH backfeeds the SIM800 through its ESD protection diodes and partially powers it even with the MOSFET cut.

### Connectivity is dual-mode: WiFi or LTE

`connectionType` (persisted in SPIFFS as `/connType.txt`) selects between two parallel code paths everywhere data is sent or config is received:
- WiFi: `WiFi.h` + `wificlient` (`PubSubClient` over `WiFiClient`) — `sendDataWiFi()`, `wifiReconnect()`.
- LTE: `TinyGsmClient` (SIM800 via `SerialAT`/`Serial2`, RX2=16/TX2=17) + `simclient` (`PubSubClient` over `TinyGsmClient`) — `sendDataLTE()`, `simReconnect()`, plus modem power management (`modemPowerOn/Off/Restart`). The modem has no PWRKEY pulse logic — its entire power rail is gated by the P-channel MOSFET on GPIO15, so "off" is a graceful `modem.poweroff()` (AT+CPOWD) followed by cutting the MOSFET; skipping the graceful step can leave it half-registered and drawing current through the whole sleep.

Both paths converge on the same MQTT topics (`jhpAI/HIDROMET/data` publish, `jhpAI/HIDROMET/settings` subscribe) and the same `callback()` handler for receiving remote config (the topic includes the device MAC as a suffix so each device only acts on its own settings push). When adding a feature that touches networking, mirror the change in both the WiFi and LTE variants.

**Offline resilience:** if a publish fails, `init_running()` calls `appendPendingRecord()` to append the JSON payload as a line to `/pending.jsonl` in SPIFFS instead of dropping it. Before publishing the *current* reading, both `sendDataWiFi()` and `sendDataLTE()` call `flushPendingData()`, which replays pending lines in order over the already-connected MQTT client; on the first failed publish it stops and rewrites the file with only the unsent lines (via a `/pending.tmp` swap) so ordering is preserved and nothing is retried out of order.

**Time sync without an RTC chip:** this hardware has no battery-backed RTC, GPS, or NTP path, so real (epoch) time is bootstrapped from whatever device connects to the config-mode AP — the config page posts the browser's clock to `/settime`, which anchors `timeBaseEpoch`/`timeBaseRtc` against `getRtcTimeSeconds()` (the RTC slow-clock, which does survive deep sleep). Every later timestamp is computed by adding elapsed RTC-clock seconds to that anchor, so it keeps working across sleep cycles without needing a live network connection each time. `syncTimeFromInternetWiFi()`/`syncTimeFromInternetLTE()` opportunistically re-anchor after a successful publish when network time is available.

### Sensors

Sensors are individually toggled via boolean flags (`A_TH`, `A_WS`, `A_PR` — temp/humidity, wind, rain) persisted in SPIFFS and configurable from the web UI or remote MQTT config push. `readSensors()` builds the JSON payload sent over MQTT; `updateSensCache()` is the parallel path that refreshes `sensCache` for the live `/sensors` JSON endpoint used by the config-mode web UI (non-blocking polling, refreshed every 15 s from `loop()`).

- The temp/humidity sensor (GPIO4) is compiled as `DHT_TYPE DHT21` (AM2301) — a single-wire digital sensor that does *not* share the I2C bus. Readings outside the DHT22/AM2301 physical range (`DHT22_TEMP_MIN/MAX`, `DHT22_HUM_MIN/MAX`) are discarded rather than propagated.
- Wind direction is read from whichever encoder `dirSensorType` selects (`"MT6701"` or `"AS5600"`, persisted in `/dirSensor.txt`, settable from the web UI or MQTT config push) — both drivers are always initialized/compiled, `WindDirection()` just branches at read time. Only this subsystem uses I2C (SDA=21/SCL=22); `Wire.begin()` is gated behind `A_WS`, not `A_TH`.
- Wind speed (`WindVelocity()`) is a blocking ~3 s falling-edge pulse-counting loop on GPIO13 (Hall sensor, push-pull, `INPUT_PULLUP` used only to hold a solid HIGH when disconnected). Pulses are converted via `WIND_SPEED_PER_PULSE` (cup radius + empirically wind-tunnel-derived `WIND_CAL_FACTOR`), debounced by `WIND_PULSE_DEBOUNCE_US` (8 ms — a stationary magnet sitting on the sensor can chatter across the comparator threshold), and any result above `MAX_WIND_SPEED_MS` is discarded as sensor noise rather than reported. `updateSensCache()`'s non-blocking config-mode variant uses the same debounce constant via `windPulseISR()`.
- Operation-mode readings are multi-sampled and averaged: T/H takes `TH_SAMPLES` (3) valid reads every `TH_INTERVAL_MS` (1.1 s, below the DHT's nominal 2 s — `readDHT22(..., force=true)` bypasses the Adafruit library's 2 s result cache, which would otherwise return the same reading); wind uses `readWindAveraged()` — `WIND_SAMPLES` (2) `WindVelocity()` windows, each calibrated with `windCal()` before averaging (implausible windows return `NAN` and are excluded), plus one direction sample per window. `windCal()` returns 0 for 0 pulses: the calibration line has a 0.53 m/s intercept that used to be reported with the cups stopped or the sensor unplugged. Direction is averaged **circularly** (`circularMean()`, unit-vector sum + `atan2`, so 350° and 10° average to 0°, not 180°); if the samples spread more than `WD_MAX_SPREAD_DEG` (36° = 10 % of 360°, wrap-aware `angleDiff()`), up to `WD_EXTRA_SAMPLES` more are taken and the last `WIND_SAMPLES` consecutive stable ones are used; if it never stabilizes ("oscillating"), the range widens to `WD_OSC_SPREAD_DEG` (90° = 25 %) and `largestAngularCluster()` averages the largest group of samples fitting in that arc (must be more than half of them, so isolated gusts are dropped), and only otherwise falls back to the circular mean of all samples. 359° and 0° count as 1° apart everywhere (both north). RAD and SOIL average `RS485_SAMPLES` (2) Modbus reads; rain just reads the counter. The config-mode live cache (`updateSensCache()`) still takes single reads.
- Rain is a Hall sensor on GPIO39 (EXT1 wakeup source, input-only RTC GPIO with no internal pull resistor — needs an external pull for a fully clean signal). Because the idle/field voltage gap is close to the ESP32's digital-input threshold, code prefers reading raw ADC millivolts (`RAIN_ADC_FIELD_MV`/`RAIN_ADC_IDLE_MV`, with a 500–1500 mV dead zone) over `digitalRead()` where possible; the persisted count is reset to 0 once read. See `runRainCounter()` (deep-sleep path) and `rainPulseISR()` (config-mode live-counting path, which re-implements the same two filters since config mode never sleeps).
- Sensor power (temp/humidity, wind speed, wind direction encoder, OLED) is gated by a P-channel MOSFET on GPIO2 (`HIGH` = OFF, `LOW` = ON); modem power on GPIO15 is NPN-driven (`HIGH` = ON, `LOW` = OFF).
- Battery voltage (`vBat()`, GPIO34) averages 16 `analogReadMilliVolts()` samples and multiplies by the 330k/100k divider ratio (×4.3). The result is multiplied by `batCalFactor` (`/batCal.txt`, 0.5–1.5), set from the config portal's "Calibración de batería" card by entering a multimeter reading (factor = real / `vBatRaw()`). An earlier wrong 390k/100k ratio read 4.67 V for a ~4.0 V battery. `vBatQuick()` (4 samples, used by the modem diagnostics) applies the same factor. The OLED status bar shows battery volts, not %.
- An SD card on the default VSPI pins (MISO19/MOSI23/SCK18/CS5) is mounted at boot (`initSD()`) and used as a local backup log (`logToSD()` appends the JSON payload as a CSV row to `/datalog_v3.csv` — the file is renamed (`datalog.csv` → `_v2` for the RS485 columns → `_v3` for `LV`) whenever columns change, so old and new rows aren't mixed under one header — on every cycle in `init_running()`, independent of whether the MQTT send succeeds). `formatSD()` uses the ESP-IDF FAT VFS APIs directly (not the Arduino `SD.h` API, which has no format operation) to recover cards without a valid filesystem.

### Persistent config (SPIFFS)

All runtime settings (WiFi creds, MQTT broker/topics, sleep period, sensor enable flags, wind-direction sensor selection, connection type, APN, rain counter, time-base anchor) are individual flat files in SPIFFS (e.g. `/timesleep.txt`, `/A_TH.txt`, `/dirSensor.txt`), read/written via the `readFile`/`writeFile`/`saveSetting` helpers. `createDefaultConfigs()` seeds defaults on first boot. There is no structured config blob (no single JSON config file) — each setting is its own file, written only when changed (`saveSetting` short-circuits on no-op writes to limit flash wear).

### Config-mode web UI

`index_html` (a single inlined `PROGMEM` HTML/CSS/JS string) is templated via `ESPAsyncWebServer`'s `processor()` callback (`%PLACEHOLDER%` substitution reading directly from SPIFFS files) and polls `/sensors` (JSON) every 5 s client-side. Form submits go through `/get` with query params; saving any setting redirects back to `/`. The page also posts the browser's clock to `/settime` on load to anchor real time (see time-sync note above). There's no separate static asset pipeline — editing the UI means editing the raw HTML string in `main.cpp`.

### OLED + buttons

The OLED is used in portrait (`OLED_ROTATION`, 64x128 px = 10 columns x 16 rows of the 6x8 font) as a minimal dashboard drawn by `dashDraw()` from the global `dash` state: status bar (battery icon + %, signal bars from CSQ/RSSI), mode + link type bar (OPER/CONFIG/ESTADO, LTE/WIFI/SD), one row per **enabled** sensor only (`A_TH`, `A_WS`, `A_PR`, `rs485Type`), and a process area (current step + 2 detail lines + progress bar). `dashBegin(mode, steps)` resets it (`dashStepsFor()` gives the step count per link type), `dashStep()` advances the sequence, `dashFinish()` shows the final result, `dashSet()` updates one sensor value, and `oledLog()` only sets the detail lines (keep those texts ≤ 20 chars). All are no-ops when `oledReady` is false. `oledInfoPage()` renders key/value detail pages. Because the OLED is powered from v_sensor, showing progress in operation mode keeps the sensor rail on for the whole cycle — gated by `/oledOp.txt` (web UI checkbox, or `"oled"` in the MQTT config push). Config mode (`configOledTask()`) and the EXT0 status viewer each have 3 views (dashboard / network / system); UP/OK short = next/previous view, OK long (2 s) = restart into operation mode (config) or run a cycle now (status viewer). Strings shown on the OLED must be ASCII (no accents): the default GFX font has no UTF-8. Modem/connectivity progress on the OLED is plain language for a basic user (`mdiagShow(code, msg, tech)`: `code`/`tech` go only to serial + `modemStep`; `msg` is the OLED text). On LTE failure `modemDiagFail()` shows `drawModemFriendlyPage()` (problem + what to do, from the `NET_FRIENDLY` table mapping `lastNetStatus`); UP toggles the technical `drawModemDiagPage()`. The status viewer has both as views 3 (friendly) and 4 (technical).

### RS485 sensor

`rs485Type` (`/rs485.txt`: `NONE`/`SOIL`/`RAD`/`LEVEL`, validated by `rs485Norm()`, set from the web UI select or `"rs485"` in the MQTT config push) picks the Modbus RTU sensor at slave address 1: `SOIL` = 4-in-1 soil probe at 9600 baud (regs 0..3 → JSON `SH`,`ST`,`EC`,`PH`), `RAD` = pyranometer at 4800 baud (reg 0 → `RAD`, W/m²), `LEVEL` = ACLT600 ultrasonic level sensor at 9600 baud (reg 0x0001 → `LV`, raw int16 averaged, no scaling; protocol taken from the `levelSIM7000` project). `LEVEL` needs `LEVEL_WARMUP_MS` (10 s) after rail-on, then `readLevel()` reads until `LEVEL_STABLE_WINDOW` consecutive values are within `LEVEL_STABLE_THRESHOLD` and averages `LEVEL_AVG_SAMPLES` more; unlike the reference it aborts on the first failed read / `LEVEL_MAX_FAILS` in a row so an absent sensor can't keep the device awake for minutes. `readRS485(d, live)`: `live=true` (config-mode cache) leaves the 12V rail on between reads and skips the stabilization phase. `modbusReadRegs()` builds the request with a computed CRC and validates address/function/length/CRC of the reply. The sensor's 12V boost is switched by GPIO14 (`rs485RailOn()`/`rs485RailOff()`), independent of the modem; `readRS485()` waits `RS485_WARMUP_MS` from rail-on (`rs485RailOnMs`) and cuts it afterwards (except `live`). If the sensor doesn't answer, the TX/RX orientation is swapped and remembered in `RTC_DATA_ATTR rs485Swapped` (the schematic's TXD/RXD naming is ambiguous). Both MQTT clients call `setBufferSize(768)` — PubSubClient's 256-byte default is too small for the payload with RS485 fields and `publish()` fails silently.

### Power management (battery operation)

The SIM800's 2 A TX bursts sag VCC (1S Li-ion → SX1308 boost → SIM800; the ESP32 is fed from the same VCC through the DevKit's AMS1117, which has ~1 V dropout), so the firmware defends against brownouts:
- `modemRailOn()` can soft-start `sim_control` with an LEDC PWM ramp (`MODEM_SOFTSTART_MS`), currently **0 (direct switch)** to match the PROD commit `a603f7a`, which connected reliably; used by `modemPowerOn()`. `initVariant()` (core hook, runs before `setup()`) forces GPIO15 LOW as early as possible, because its strapping pull-up turns the modem rail on during reset.
- `networkSkipReason()` decides per cycle whether to attempt sending: skip after a brownout reset (`esp_reset_reason()`), skip LTE when resting battery `cycleBatV < BAT_MODEM_MIN_V`, and exponential backoff (every 2/4/8 cycles) once `netFailStreak` (SPIFFS `/netFail.txt`, so brownout resets don't wipe it) reaches 2. A cold boot (`ESP_RST_POWERON`/`EXT`/`SW` — battery reconnected, EN button, USB flash) resets the streak to 0 so bench testing after a power fix sends immediately. Skipped cycles still log to SD and queue to `/pending.jsonl`.
- Below `BAT_CRITICAL_V` the sleep period is multiplied by `LOW_BAT_SLEEP_FACTOR` (`RTC_DATA_ATTR sleepFactor`, applied through `configuredSleepPeriod()` so rain/button wakes stay consistent).
- All battery thresholds are ignored when `vBat()` reads below `BAT_VALID_MIN_V` (no divider / USB power). They assume `vBat()` has been calibrated.
- Operation mode runs at 80 MHz CPU, except in LTE mode, which stays at 240 MHz like PROD `a603f7a` (UART corruption showed up after lowering it).
- The modem session is based on PROD `a603f7a` with longer timings: rail on → `MODEM_BOOT_MS` (5 s) with the UART closed → `SerialAT.begin()` → `modemStabilize()` (M4 `AT` sync, M5 wait for `SMS Ready` or `MODEM_QUIET_MS` of silence, M6 `MODEM_STABLE_OK` clean `OK`s in a row) → `modemInitRetries()` (`MODEM_INIT_TRIES` inits without cutting power) → only then `modemRestart()` and repeat. Reason: right after boot the SIM800's replies arrived corrupted (`OK` + garbage) and TinyGSM's `ATE0` check failed. Diagnostics during power-on are passive (battery, RX/TX pin levels, shown on the OLED `MODEM` line); the AT baud-rate probe (`modemDiagProbeAT()`) only runs after both inits fail. `sendDataLTE()` logs the SIM800's own supply voltage (`AT+CBC`, `lastModemMv`); the payload carries `BO` = cumulative brownout count from `/brownouts.txt`.
- `modemPowerOn()`/`modemPowerOff()` bracket the modem session with `modemBrownoutRideThrough()` (`MODEM_BROWNOUT_RIDE_THROUGH`): the brownout detector is disabled only while the modem is on, so momentary TX-burst sags don't reset the ESP32. `modemStepSet()` records the current modem step in `RTC_NOINIT_ATTR modemStep` (survives brownout/WDT resets, unlike `RTC_DATA_ATTR`), and `setup()` prints it after a non-power-on reset. `MODEM_BAND` (default `""`) optionally forces `AT+CBAND` — 1800/1900 MHz bands transmit at 1 W instead of 2 W, roughly halving the peak current.
